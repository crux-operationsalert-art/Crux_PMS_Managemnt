## 1. Objective

One tool that runs Crux's operations and its performance scheme, so that:

- a person can see what they are measured on, file it, and be scored fairly;
- a manager can set their team's measures, watch them, and act on them;
- HR and an administrator can run the scheme and keep the organisation's
  record straight;
- and nothing about somebody's pay or performance is readable by anybody who
  is not entitled to it.

## 3. Constraints

- **Egress.** This session reaches the Supabase host only through the MCP
  tools. `gh api` and anonymous `git clone` work; `github.io` does not.
- **The MCP approval gate.** Some calls need an approval this session cannot
  answer, and it is **content-based**: any statement carrying the word `drop`
  is refused through `execute_sql` and `apply_migration` alike. Roughly one
  call in three is refused at random as well, and retrying the identical call
  works. When a call cannot be made at all, the work is written, tested
  locally against the baseline, committed, and listed in §11.
- **One row, many patches.** A patch rule is `(old, new, want)`; a span rule
  is `((from, upto), new, want)`. Patches go in **before** the
  `for name, sentinel, rules in PATCHES:` loop. CSS comments inside a patch
  string must be `/* */`, never `#`. **A patch's sentinel must be a string
  that patch itself writes** — the build refuses any other, before it touches
  a line of the page.
- **`build/app/screen-plb.js` is a MIRROR.** Only the blocks between
  `/* OKR-SCORECARD-START…END */` and `/* QUARTER-AS-MONTHS-START…END */`
  are injected. The rest of that file is dead and the build refuses to run
  without the markers. `screen-perf.js`, `screen-team.js`, `screen-today.js`,
  `screen-help.js`, `screen-mytab.js` and `screen-matrix-month.js` are
  spliced wholesale.
- **Local proving ground.** PG16 on port 55432, socket `/home/crux/pg`, user
  `crux`. `build/test/run.sh` rebuilds the database from `build/schema` alone
  and runs every assertion against it. It exits non-zero if anything is
  **skipped** as well as if anything fails, because a skipped check is not a
  passed one.

## 7. Methodology

The same loop every time, and it is not negotiable:

1. **Measure first.** Never diagnose from the source alone. The claim "most
   of the buttons in PMS are not working" was settled by loading the
   published page in Chromium, signing a manager in against stubs, and
   pressing every control — not by reading `pfWire`. That instrument is in
   the repository as `build/test/page_probe.mjs`:

   ```
   npm i playwright
   git show origin/main:index.html > /tmp/published.html
   node build/test/page_probe.mjs /tmp/published.html
   SHUT=1 node build/test/page_probe.mjs /tmp/published.html
   AS_HR=1 SHUT=1 node build/test/page_probe.mjs /tmp/published.html
   ```

   It is deliberately not in `run.sh`: it needs a browser and a copy of the
   published page, and the suite has to run anywhere.
2. **Write the migration with a guard that fails loudly.** Every migration in
   `build/migration/` asserts its own invariant at the end and raises if it
   does not hold. A guard that mutates to prove a point puts the row back.
3. **Substitute over live source, never retype from memory.** Migration 239
   was written from memory and lost a clause. Since then every function
   rewrite either carries the live `prosrc` or is checked against it, and
   raises rather than performing a replace that silently matches nothing.
4. **Test what the user does, not what the code says.** A test that restates
   the predicate passes whenever the predicate is self-consistently wrong
   (`test_offer.sql` attempts all 96 moves for real).
5. **An offer must equal what the write allows.** Migration 242's rule. A
   control that is always refused is a defect, not a message.
6. **Ask whether anybody can reach it.** Tests prove a function is correct.
   Only measuring the **published page** proves a person can get to it —
   `build/test/reach_check.mjs`.
7. **Run the whole suite from a clean rebuild before committing.**

## 8. How the tool is built — what a new reader must know first

**The application is one row.** `app_page` (slug `app`), column `html`. The
build reads that row, applies 20 ordered patches and a shim, and writes
`index.html`. A change to `build/app/*.js`, `.github/build-tool.py`,
`.github/tool-shim.html` or `.github/app-page.sha` triggers the publish
workflow (id **359586847**, `publish-tool.yml`); the schema snapshot is
workflow **368413405**.

**Which service owns which route.** Sending a request to the wrong one is a
404 that reads to the user as a refusal:

| Service | Routes |
|---|---|
| `perf` | `/perf/target`, `/perf/target/team`, `/perf/cycle/extend`, `/perf/team/set`, `/perf/partner`, `/perf/escalate`, `/perf/escalate/act` |
| `plb` | `/perf/mapping`, `/perf/kpis`, `/perf/tree`, `/perf/assign`, `/perf/edit`, `/perf/remove`, `/perf/history`, `/perf/cycle`, `/kpi/months`, `/kpi/parts`, `/sheet/measures` |
| `crux` | the page itself, sign-in, OGL, evidence, uploads, mail settings, the data reset |

**Who may set whose measures.** `perf_rel(actor, person)` answers `'self'`
→ `'admin'` → depth-1 `'manage'` → `'watch'` → null, and **`'self'` is
answered before `'admin'`**, so nobody — not even an administrator — sets
their own. `perf_may_set` is `rel ∈ ('manage','admin')`. Running the scheme
(`maySetUp`, `plb_runs_scheme`) is a different question with a different
answer: an administrator, or the Human Resources or Business Excellence
department.

**Two clocks, and they are not the same question.**

- `maySet` — the reporting line. It does not move when a date passes.
- `mayEdit` — the line **and** the clock: `perf_assign`, `perf_assign_edit`
  and `perf_assign_remove` all answer `window_closed` once
  `current_date > perf_cycle.assign_closes`, for anybody but an
  administrator. Answered once, server-side, by `perf_mapping` (259).
- The quarterly sheet is governed by neither. It is editable until the sheet
  **locks**.

**How a number is worked out.** None of this was rebuilt; all of it was
reused.

- `perf_value(assignment, depth)`: if the measure has children, `SUM` →
  `sum(perf_value(child))`, `LEVEL` → target-weighted average
  `Σ(cv × child.target) / Σ(child.target)`. With no children it reads
  `perf_entry` (sum for SUM, latest for LEVEL). Then it adds anything whose
  `rolls_into_id` points at it.
- `perf_accrual_kind`: explicit `replace|level|latest|last|avg|aver` → LEVEL;
  a unit matching `%|score|rate|ratio|pct|percent|per cent` → LEVEL;
  otherwise SUM.
- `perf_ratio(direction, target, actual)` — `LOWER`: target 0 → (actual 0 ?
  100 : 0); actual 0 → 150; else `least(150, 100 × target / actual)`.
  `HIGHER`: target 0 → (actual > 0 ? 150 : 100); else
  `least(150, 100 × actual / target)`. **The payout curve has not moved.**
- `perf_file` refuses a filing on a parent: `{"error":"has_parts"}`. A total
  typed in beside its own parts is how two right numbers make a wrong one.

**A sub-KPI needed no schema change.** `perf_assignment.split_kind` already
allowed `CLIENT | BRANCH | PLACE | OTHER`, and `OTHER` is the slot for a
named breakdown. No table, column or constraint was added for sub-KPIs.

**Every jsonb parameter is sent as text and cast on the server.**
postgres.js mis-types a JS string bound to `$n::jsonb`. The fix is
`coalesce($n::text,'{}')::jsonb` server-side with an `asObject()` helper
client-side, applied to every jsonb bind in `perf` and `plb`.

**`call()` cannot reject.** It is the single function every service request
goes through, so a rejection there is a screen stuck on "Loading…" rather
than a message.

## 9. The Performance & appraisal rebuild — the owner's specification, and what it became

> "The current KPI/target assignment journey is too complicated. Redesign the
> journey to be extremely simple: **My Team → Select Person → Performance
> Mapping → Monthly | Quarterly → Manage Scorecard.** Nothing more."

| The specification | What is live |
|---|---|
| The journey, and no intermediate pages | `My Team → person → Performance Mapping`, in the Performance & appraisal screen. `pfPersonPanel()` is now one line: `return pfMapping();` |
| Previous achievements behind a simple `+` | `pfMapHistory()`, collapsed, reading `/plb/perf/history` |
| Minimum 3, maximum 5 KPIs; no add button at 5 | `perf_kpis_set` validates the whole list; `rules.mayAdd` is answered server-side |
| Row = KPI · Weightage · Target · Frequency · Edit · `+` | `pfMapRow()`, exactly those six columns |
| `+` adds a sub-KPI inline; the parent greys, locks, reads "Derived from Sub-KPIs" | `pfMapSubForm()` / `pfMapSubRow()`, using `perf_value`'s existing SUM and LEVEL logic |
| Target = **one** input box, not month-wise boxes | one `data-pfmt` box per row |
| Total weightage always 100%, shown prominently, saving prevented otherwise | the table foot, and `perf_kpis_set` refuses the save |
| Quarterly: the same journey and UI, M1 \| M2 \| M3 instead of one target | the Quarterly tab of the same panel, `pfMapQuarterly()` |
| Past months greyed, read-only, showing the actual achievement | `pfMapQCell()` — the real monthly target, what was filed, and whether the two agree with the quarter's split |
| Do **not** blindly rebuild | no table, column or constraint was added for any of it |

**Two rules are not literal, and the live data is why.**

- **100% means ±0.1.** 76 of 101 people carrying October measures differ from
  100 only by rounding (the live range is 99.99–100.02; three equal weights
  are 33.33 × 3 = 99.99). An exact test would refuse three-quarters of the
  company a save.
- **Five caps *adding*, not *editing*.** Nine people carry more than five
  measures today. The cap is `greatest(5, what they already have)`, so nobody
  is shown a wall in front of a scorecard they are already holding.

**What was built underneath it**

| | |
|---|---|
| **255** | The quarterly sheet is editable until it locks. `plb_goal_kpi` became a **view** over the live rows of `plb_goal_kpi_all`, so all fourteen readers go on saying `plb_goal_kpi` and read only live rows with not one of them touched. `plb_sheet_measures_set` replaces the whole list in one call, because the rule that validates it — the weights add to a hundred — is a rule about the set. |
| **256** | The October window runs to the **15th**, through `perf_cycle_extend` so that who reopened it and why is recorded. `crux-perf-reminders` and `crux-matrix-nudge` are paused; `crux-mail` is deliberately left running — it is the sender, not a mailer, and stopping it would stop activation codes too. |
| **257** | `perf_kpis_set` — the monthly twin of `plb_sheet_measures_set`. It validates the whole list and then writes row by row through `perf_assign`, `perf_assign_edit`, `perf_target_set` and `perf_assign_remove`; it writes nothing itself. `perf_mapping` returns the tree plus the quarter, the sheet id and the rules, so the page does not re-derive them. |
| **258** | A sub-KPI can be renamed. `perf_assign_edit` refused to rename any part; it now refuses only `CLIENT`/`BRANCH`/`PLACE` — one client's share of a measure is not a measure — and a renamed `OTHER` part moves both its name and its label. |
| **259** | A shut month stops offering what it will refuse. `perf_mapping` answers `mayEdit` and `assignCloses`; the panel's three monthly checks read it, and a shut month says so where Save would have been, with the date and who can reopen it. |

## 12. Risks and known limitations

| | Risk | Standing |
|---|---|---|
| R1 | The application is one ~717 KB row with 20 patches applied at build time | Every patch asserts its own call-site count, and the build refuses any patch whose sentinel appears in none of its own rules. A build fails loudly rather than publishing a page it did not understand. |
| R2 | A function rewritten from memory loses a clause | Migration 239 did exactly this. Mitigated by substituting over live `prosrc`, with a raise if the anchor is not found. |
| R3 | Three independent line walkers — `perf_line`, `org_subtree`, `app_subtree` | They can disagree. 245 keeps the service-account rule in the table so none of them needs to know about it. |
| R4 | 6 of 108 staff have no manager, 3 no designation | Not a code defect, but `perf_rel` is built on `manager_id`. **All people** exists to find and fix it. |
| R5 | Aniket Chalke has **42** direct reports, and the reporting line has **six** roots — six people with no manager at all | A data shape nobody chose. Worth the owner's decision (Q1). |
| R6 | **A check that cannot run is not a check** | `window_check.mjs` threw a `ReferenceError` before its first assertion for six days, because its harness named a renderer that had been deleted — and the suite counted that as one failure among hundreds while the thing it guarded quietly stopped being true. `run.sh` now exits non-zero on a **skipped** check as well as a failed one, and the whole suite is run from a clean rebuild before every commit. |
| R7 | A feature can be published and unreachable | Four times in one fortnight. `reach_check.mjs` now asserts that 15 named features are reachable **from the screen the owner is told to open**. Its own limitation is documented in the file: reachability is name-occurrence, not control flow, so it errs towards "reachable" and will miss dead code — it cannot raise a false alarm, and it cannot catch tidiness. |
